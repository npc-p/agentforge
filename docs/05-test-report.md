**测试对象**：AgentForge 智能体研发平台（后端 + 前端）

## 6. 评测集结果

### 6.1 检索质量（5 用例，真实数据）

**换嵌入模型前后跑同一套件**（同批数据、同 `top_k=6`，2026-10-28 实测）：

| 指标 | 哈希 512 维（基线 run 3） | **BGE-M3 1024 维（run 4）** | 达标线 |
|---|---|---|---|
| `hit_rate` | 0.8 | **1.0** | ≥ 0.95 ✅ |
| `hit_rate_top1` | —（当时未采集） | **0.8** | — |
| `mrr` | 0.6667 | **0.9** | ≥ 0.9 ✅ |
| 通过数 | 4 / 5 | **5 / 5** | — |
| 延迟 avg / p95 | 4.0 / 9.0 ms | **56.6 / 70.0 ms** | — |

为排除 BM25 对判断的干扰，另做了一次**纯向量**对照（`scripts/compare_embedder.py`，
只算查询与切片的余弦排序，不含 RRF）：

| 用例 | 哈希排名 | BGE-M3 排名 |
|---|---|---|
| 循环最多能跑几圈 → 「8 轮」 | 4 | **1** |
| 轻微问题会不会整条作废 → 「扣减」 | **13（掉出 top6）** | **2** |
| 混合检索怎么融合 → 「RRF」 | 2 | 2 |
| 去重的阈值怎么定 → 「SimHash」 | 1 | 1 |

```json
{"mrr": 0.9, "total": 5, "errors": 0, "passed": 5, "hit_rate": 1.0,
 "pass_rate": 1.0, "hit_rate_top1": 0.8, "latency_avg_ms": 56.6, "latency_p95_ms": 70.0}
```

**代价**：CPU 单次推理从 4 ms 增加到 56.6 ms（约 14 倍），首次调用还需约 30 s
加载 2.2 GB 权重（已做懒加载，只在首次使用时发生）。

**结论**：零字面重叠的困难用例从「排名 13、实际搜不到」变为「排名 2、落在 top6 内」，
这是从**检索失败**到**检索成功**的跨越，而不是排序上的微调。代价是 CPU 单次推理增加
约 50~90 ms，且模型加载占 2.2 GB 内存。

**仍未解决的部分（诚实披露）**：`hit_rate_top1` 只有 0.8，两条零重叠用例仍有 1 条
排在第二位而非首位。进一步改善需要 Rerank（cross-encoder 重排），见
`docs/04-optimization.md` P1 行。

### 6.1.1 标题切片抢占首位（已修复）

**现象**：切分把 Markdown 标题单独切成一块（如 `# 检索增强设计`，仅 9 字），它在语义空间里
与多数相关查询都有中等相似度，于是经常抢占首位——实测「混合检索怎么融合」的 top1 是标题块，
而含 RRF 说明的正文块被挤到第 2。

**根因在切分，不在检索**：标题本属于它引出的那段内容，却被切成了独立片段。因此在检索层
加权只是打补丁，正确做法是让标题**向下并入**正文（`splitter._merge_headings`），同时补上
「无 `#` 前缀的短首块」也应并入后一段。

**修复后实测**：

| 维度 | 修复前 | 修复后 |
|---|---|---|
| 纯向量 hit@1（4 条查询） | 2/4 | **3/4** |
| 切片总数 | 14 | **11**（−21%） |
| 混合检索 hit_rate / top1 / MRR | 1.0 / 0.8 / 0.9 | 1.0 / 0.8 / 0.9（**未变**） |

**必须如实说明**：混合检索的最终指标没有变化。原因是那条被标题挤占的查询，原本就靠 BM25
拿到了首位，向量排序的改善被融合掩盖了。修复的真实收益是：切断了向量路径上的排序污染、
切片数减少 21%、以及引用展示不再出现「只有一行标题」的片段。

**关于 Rerank 的验证（2026-10-28，结论：不接入）**

针对那条未达 top1 的用例试了 cross-encoder 重排（`BAAI/bge-reranker-base`，278M 参数）：

| 查询 | rerank 后排名 | 打分耗时 |
|---|---|---|
| 循环最多能跑几圈 | 第 1 名 | ~530 ms |
| 轻微问题会不会整条作废 | **第 2 名（未改善）** | ~540 ms |
| 混合检索怎么融合 | 第 1 名 | ~530 ms |
| 去重的阈值怎么定 | 第 1 名 | ~550 ms |

`hit@1` 仍是 3/4。原因是这条查询与两个片段都相关（总述块提到「质检」，细节块提到「扣减」），
cross-encoder 也偏好总述块——这属于**语义相近的强干扰**，重排解决不了，需要答案级理解。

代价则是每条查询增加 280~560 ms（现检索均值 56.6 ms）。**收益为零、成本翻数倍，因此不接入**，
只保留 `scripts/compare_rerank.py` 供复现。这个「验证后明确不做」的结论，比盲目加一个模型更有价值。

剩余 1 条未达 top1 的用例（「轻微问题会不会整条作废」排第 2）是真实的语义近似——它被
「去重」块挡住，而两块都包含质检相关内容。这需要 Rerank 而不是切分优化。

| 评测测不出答非所问 | 新增 `evaluation/judge.py`，套件 `config.judge=true` 时启用，与关键词断言**同时通过**才算通过 | 3 条 judge 单测（correct / off_topic / 不可解析降级） |

期间还修掉一个自己引入的缺陷：`stage_groundedness` 调用 `judge_sample` 时把 `score_threshold` 写成 `threshold`，
单测直接调用 `judge_sample` 覆盖不到这条路径，靠真实调用才发现——已补阶段级测试防回归。

**复查补漏（第二轮审计）**：对上一轮修复做回归探测时又发现三处：

| 问题 | 修复 | 验证 |
|---|---|---|
| `SHOW DATABASES`、`SELECT @@version` 仍被放行（实例信息泄露，与"已收口"的表述不符） | SHOW 只放行表结构族；禁止 `@@` 系统变量 | 三类元信息查询均被拒，`SHOW TABLES` 正常 |
| 新增的 `hit_rate_top1` 前端未展示（后端改了、界面看不到） | 评测页增加指标卡 + 类型定义补字段 | 构建通过，页面 200 |
| 健康检查未体现只读账号隔离状态 | `database.readonly_isolated` 字段 | 返回 `True` |

### 7.2 残留风险（已知且未消除）

1. **闸门已扩展到「成功但结果为空」**（`observation_is_evidence`：检索 0 命中不算证据），实测空知识库场景下模型连查 3 次、零命中后触发闸门返回固定话术。**仍存在的能力缺口**：工具返回「有结果但不相关」时无法识别——这需要答案级 groundedness 校验（见第 3 条，目前只覆盖数据侧，未覆盖在线对话）。
2. **评测已支持 LLM-as-judge**（`eval_suites.config.judge`），但**默认关闭**：开启后每用例多一次模型调用。当前基线数字仍是纯关键词口径，与历史数据可比。
3. **质检已增加答案忠实度校验阶段**（`groundedness`），实测 3 条样本全部 `supported`；但它只在**检索到相关内容（score ≥ 0.35）**时才判定，库里没有相关文档的样本仍会被标为 `insufficient` 而非错误——这属于能力边界，不是缺陷。
4. **嵌入语义空洞已解决**：嵌入模型由 512 维字符 n-gram 哈希换为本地 BGE-M3（1024 维），零重叠用例从「排名 13、搜不到」变为「排名 2、命中」（详见 §6.1）。仍有 1 条零重叠用例未达 Top1，需 Rerank 才能进一步改善。
5. 入库同步阻塞、无鉴权、日志已脱敏但未做集中采集——均已在 README「状态与限制」中如实声明。
6. **并发压测只覆盖只读路径**，写入路径（文档入库、Chroma 单进程写锁）未测。

**缺陷 6 的启示**：它在 Mock 模式下永远不会触发（Mock 直接走规则标注），
说明「用 Mock 跑通全链路」不能替代真实供应商验证。后续改动涉及 Prompt 时，必须至少跑一次真实模型。
