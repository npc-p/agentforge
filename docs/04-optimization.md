# 优化方案

> 本文只写**已实施且可复现**的优化与**明确排期**的待优化项，不含未验证的估算。

## 1. 已实施优化

### 1.1 减少模型调用次数

| 优化 | 做法 | 效果 |
|---|---|---|
| 简单问答跳过 ANSWER 节点 | 决策阶段已产出答案且无工具观察时，直接复用为最终答案 | 单轮闲聊从 2 次模型调用降为 1 次，延迟约减半 |
| 反思节点条件触发 | 仅当本轮真正调用过工具时才执行 REFLECT | 无工具场景省掉 1 次调用 |
| 重复调用抑制 | `tool_signature(tool,args)` 与历史观察比对，命中即拦截 | 避免模型反复调同一工具，直接省 token 与超时等待 |

**为什么值得做**：一次 Agent 问答的调用链是 Plan → Decide(+工具) → Reflect → Answer，
共 4 次模型调用。前两项优化把最常见的「简单问答」降到 1 次、「单工具问答」降到 3 次。

### 1.2 检索侧

| 优化 | 做法 | 说明 |
|---|---|---|
| BM25 索引缓存 | 以「知识库集合 + 代数」为键缓存，写入时 `bump_generation()` 失效 | 避免每次查询全量重建索引；实测首次检索 p95 876ms，命中缓存后进入几十毫秒级 |
| 正文以 MySQL 为真相源 | 向量库只返回 id，正文按 id 批量回查 | 消除两处数据不一致时引用到过期内容的风险 |
| 切片批量嵌入 | 每批 32 条，`flush()` 拿自增 ID 后写向量库 | 减少往返次数，同时保证向量 id 与 chunk id 一致 |
| 文档级内容去重 | 入库前校验 sha256，重复即返回 409 | 避免重复上传导致同一内容多份切片污染召回 |

### 1.3 数据侧

| 优化 | 做法 |
|---|---|
| 阶段幂等 | 每阶段只处理上一阶段完成的样本，重复执行不重复加工（去重阶段另有自比对防护） |
| 弱信号降级而非否决 | 质检规则分 error / warning，warning 只扣分 | 
| 标注失败降级 | LLM 标注异常自动退化为规则标注，流水线不中断 |
| 版本快照 | 导出即冻结质量指标，支持「换规则后效果是否变好」的量化对比 |

### 1.4 可靠性

| 优化 | 做法 | 参数 |
|---|---|---|
| 模型重试 | 仅对超时/连接/429/5xx 重试，指数退避 | `llm_max_retries=2`，0.5s/1s/2s |
| 熔断 | 连续 5 次失败打开，30s 后半开探测 | `llm_circuit_threshold=5` |
| 模型降级 | 无 Key 自动切 Mock，UI 显式标注 | — |
| 流式降级 | 流式中断则改一次性返回，答案不丢 | — |
| 数据库连接池 | `pool_pre_ping=True`、`pool_recycle=1800` | `pool_size=10, max_overflow=20` |

## 2. 待优化项（按投入产出排序）

| 优先级 | 项 | 预期收益 | 成本/风险 |
|---|---|---|---|
| ~~P0~~ ✅ **已完成** | 嵌入模型换 BGE-M3（本地 `EMBED_PROVIDER=bge-m3`） | **实测（2026-10-28，同一套件同批数据）**：hit_rate 0.8 → **1.0**、MRR 0.667 → **0.9**、通过 4/5 → **5/5**，两条零重叠用例排名 4→1、13→2（跨过 top_k=6 门槛，从搜不到变为搜到）。实现上只用 torch + transformers 自己取 CLS 向量，不引入 sentence-transformers 整套依赖 | **代价**：CPU 单次推理 4 ms → 56.6 ms（p95 70 ms），首次调用加载 2.2 GB 权重约 30 s（已懒加载）；维度 512→1024 须重建索引；集合名带模型后缀以支持灰度回退 |
| ~~P1~~ ✅ **已完成** | 标题切片向下并入正文（`splitter._merge_headings`） | 标题单独成块时语义相似度虚高，会抢占首位把答案块挤出。修复后纯向量 hit@1 2/4 → **3/4**，切片数 14 → **11**（−21%）；混合检索指标未变（该查询原本靠 BM25 已命中首位） | 切分策略变更需重跑 `scripts/resplit.py` 重切入库 |
| ~~P1~~ ✅ **已完成** | 启动时后台预热嵌入模型 | 首问从 **9.7 s** 降到 **0.3 s**；预热在 lifespan 里异步进行，不阻塞端口监听，测试环境自动跳过 | 启动后约 10 s 内完成，占用约 2.2 GB 内存 |
| ⚠️ **已验证 · 决定不接入** | Rerank（bge-reranker-base，cross-encoder 重排） | **实测无收益**：对全部切片重排后 hit@1 仍为 **3/4**，那条难题（「轻微问题会不会整条作废」）依然排第 2 —— 它同时与「# 数据流水线规范」和「## 质检」相关，cross-encoder 也选了前者。而代价是每条查询 **+280~560ms**（当前检索仅 56ms，等于翻 6~10 倍）与 **+1GB 内存**。复现：`scripts/compare_rerank.py` | **判断依据**：Rerank 只在「召回对了但被表面词面误导」时有效；本例是语义相近的强干扰项，排序模型分不开，需要的是答案级理解而不是重排。若将来评测集扩大后出现「召回对、排序错」的样本，再重新评估 |
| P1 | 文档入库异步化（队列 + 任务状态轮询） | 大文件上传不再阻塞请求，支持并发入库 | 需引入任务表与 worker，复杂度上升 |
| P2 | BM25 增量索引 | 当前数据指纹变化后全量重建，语料万级以上时明显 | 需维护倒排增量合并逻辑 |
| ~~P2~~ ✅ **已完成** | 评测接入 LLM-as-judge | 关键词匹配无法评估语义等价；现由 `eval_suites.config.judge=true` 开启，与关键词断言叠加判定 | 评测成本上升，故默认关闭 |
| P2 | 检索结果缓存 | 重复问题（FAQ 场景）可直接命中 | 需要失效策略，避免答案陈旧 |
| P3 | 流式工具调用（边生成边执行） | 多工具串行场景降低首字延迟 | 需要在 SSE 层重构事件顺序 |
| P3 | 多租户与 RBAC | 生产化的前置条件 | 涉及全表加租户维度，改动面大 |

## 3. 容量与性能现状

| 指标 | 实测值 | 条件 |
|---|---|---|
| 单次检索延迟（冷启动） | 876 ms（p95） | 首次查询，含 BM25 索引构建 |
| 单次检索延迟（热缓存） | **4.6 ms** | BM25 索引命中缓存后，同一知识库连续查询 |
| 单次检索延迟（均） | 294 ms | 2 个知识库、19 个切片，含一次冷启动 |
| Agent 单轮耗时（均） | 3818 ms | 真实 DeepSeek，含 Plan+Decide+工具+Reflect+Answer |
| Agent 单轮 tokens | 1999 输入 / 206 输出 | 知识问答 + 1 次工具调用 |
| 单元 + 接口测试耗时 | 6.9 s / 82 条 | 本地 MySQL，Mock 模型 |
| 文档入库（400 字） | 41 ms | 含切分、嵌入、双写 |
| DOCX 解析入库（37 KB） | <1 s | python-docx，含表格抽取 |

### 并发压测结果（`scripts/bench.py`，零外部依赖）

| 场景 | 并发 | 请求数 | 吞吐 | p50 | p95 | 错误率 |
|---|---|---|---|---|---|---|
| `/api/knowledge/search` | 1 | 30 | — | 5.05 ms | 5.77 ms | 0% |
| `/api/knowledge/search` | 20 | 400 | **179 req/s** | 84 ms | 234 ms | 0% |
| `/api/knowledge/search` | 50 | 600 | **133 req/s** | 239 ms | 1017 ms | 0% |
| `/health`（无检索开销） | 1 | 50 | — | 2.07 ms | 2.35 ms | 0% |
| `/health`（无检索开销） | 20 | 600 | **223 req/s** | 78 ms | 176 ms | 0% |
| `/health` | 100 | 2000 | — | 381 ms | 2072 ms | 0.05% |

**关键结论**：空接口 `/health` 与检索接口的吞吐是同一量级（223 vs 179 req/s），
说明**瓶颈不在检索逻辑，而在 HTTP 层**——即单 worker 进程 + ASGI 中间件栈，
而非 Chroma / BM25 / 嵌入计算。证据是：检索接口在 20 并发下的增量成本仅为
`104ms − 84ms ≈ 20ms`，占总延迟不到 20%。

**由此得出的优化优先级**（与直觉相反）：提升吞吐应先增加 worker 进程或换 uvicorn 多进程部署，
而不是优化检索算法。这一点未验证——因为 Chroma 的 PersistentClient 是多进程共享同一
SQLite 文件，多 worker 下有写冲突风险（见架构文档「已知限制」）。

**仍未验证**：并发**写入**（文档入库）时的表现。检索是只读路径，写路径要过 Chroma 的单进程
写锁，预计远低于上表数字。

## 4. 成本控制

单轮问答的模型成本构成：Planner 约 120 输入 tokens、Decide 约 200-600（含工具 Schema）、
Reflect 约 80、Answer 约 300-800。优化后的关键结论：

1. **工具 Schema 是隐性成本大头**：5 个工具的全量 Schema 每次决策都会随请求发送。
   工具数量增长到 20+ 时应改为「按意图预筛工具子集」再传入；
2. **简单问答省一半**：见 §1.1，这是当前 ROI 最高的优化；
3. **重复调用拦截直接省钱**：一次多余的工具调用 = 一次额外的 Decide + 工具执行；
4. 若后续接付费 Embedding，应在入库侧做内容去重（已实现 sha256 去重）避免重复计费。

## 5. 可扩展性

| 维度 | 当前 | 扩展方式 |
|---|---|---|
| 工具数量 | 5 | `@tool` 装饰器 + 包入口 import，无需改 Agent |

| 评测 | retrieval / agent | 新增 suite type + 执行分支 |
